# Tab5 MeOS FPGA — 開発目的と開始記録

更新日：2026-10-24

## 目的と範囲

主目標を、FPGAによる描画支援を組み込んだMeOSのGUI化とする。Tab5上で、ウィンドウ、メニュー、文字、画像を扱うGUIを構築し、Tang Primer 20Kとその128MB DDR3を描画処理・画像資源の保持に活用する。文字中心の操作環境から、初期Windowsのようなウィンドウ操作環境への発展を目指す。Windows互換性は要件に含めない。

MeOS側は入力、ウィンドウ管理、アプリの状態、描画命令の生成を担当し、FPGA側は矩形塗りつぶし、画像コピー、合成などを段階的に担当する。具体的な分担は転送時間を含む測定で決める。既存の上流GUI・コンソール・表示ドライバを調査し、利用できる部分を土台にする。

大容量データの分割処理、明示的な退避・復元、演算アクセラレーションは、GUI基盤と共通する転送・バッファ管理を活用する副次的な研究対象とする。

Linux版とMeOS版を別リポジトリで管理し、通信プロトコル、データ照合、評価条件を整合させる。OSごとのAPI・メモリ管理・スケジューラ・DMA対応は個別に調査する。Linux用ドライバをそのまま利用できるとは扱わない。

FPGA側DDR3は明示的に転送する外部データ領域であり、通常のCPUポインタで参照できる主記憶や透過的なmalloc領域とは扱わない。GPU用と外部RAM用の同時搭載は初期の要件とせず、資源・帯域の評価後に判断する。

## GUI化の段階と評価

1. **基準環境**：MeOSのTab5向けビルドと表示経路を確認し、CPU描画の所要時間と内部RAM・PSRAM使用量を記録する。
2. **通信とDDR3**：小さなデータの往復照合から開始し、転送の安定性・実効帯域・DDR3のデータ保持を確認する。
3. **最小描画支援**：FPGA側バッファへの矩形塗りつぶしと画像コピーを実装し、Tab5画面に結果を表示する。命令送信・実行・画像回収・表示を含む所要時間をCPU描画と比較する。
4. **GUI統合**：MeOSの描画APIにCPU実装とFPGA実装の切替を設け、ウィンドウの表示・移動、メニュー、文字・画像表示を検証する。画像資源の常駐と変更領域の転送を評価する。
5. **拡張**：測定結果に応じて合成、拡大縮小、追加の計算処理へ進む。

最初の到達点は、Tab5で入力操作できるウィンドウとメニューを表示し、少なくとも一つの描画処理をFPGA経由で実行できることとする。高速化の成立は別途測定で判断し、フレームレート、操作応答時間、CPU負荷、RAM使用量、転送量を記録する。

初期はTab5既存LCDへのESP32-P4経由の表示を評価する。FPGA側DDR3に画像を置いても、表示のための画像回収が帯域を消費するため、表示経路は設計上の主要な検証項目とする。FPGAからの直接表示は別途ハードウェア構成の検討が必要であり、初期の前提にしない。

### USB対応後のSSHサーバーと同時実行

USBホストの汎用化とmicroSD対応に続いて、SSHサーバーを実装する。PCからMeOSへログインし、シェル操作、ファイル転送、アプリの配置・実行・診断を行える開発経路を用意する。既存のSSHクライアントと同時実行し、サーバー側の接続を維持したままクライアントの接続・通信・終了・再接続をSSH経由でテストできることを到達条件とする。

接続ごとの入出力・シェル状態・資源所有権を分離し、LCD／シリアル／SSH間の入力競合を解消する。サーバーのホスト鍵・利用者認証、接続数・バッファ上限、切断時の資源解放、ネットワークソケットの同時使用を設計する。認証なし・暗号検証省略のサーバーにはしない。共有コンソール方式のSSHサーバーとクライアント同時動作は実装・実機確認済み。SFTPはWi-Fiで往復・RO方針を実機確認。独立PTY・execは残件。

### SSH対応後のタッチ操作

実施順はUSB受信機・USBメモリ、microSD、USB書き込み修正とハブ・複数機器対応、SSHサーバーと既存クライアントの同時動作、タッチ対応、Bluetoothキーボード・マウス対応とする。ST7121端末で上下スワイプによるコンソールスクロールを実機確認済み。画面の自動スクロールとは区別し、過去出力の保持、表示位置、最新出力への復帰、出力継続中の閲覧、画面キーボードとの入力判定を設計する。ローカルとSSH用端末の双方で利用できる共通入力経路を検討する。

### SSH経由のストレージ操作とLinuxマウント

MeOSのSSHサーバーに標準SFTP v3サブシステムを追加した。公開範囲は`/sd`、`/usb`、`/usb1`、`/usb2`、`/usb3`に限定し、既定は読み取り専用とする。方針変更はサーバー停止中の`sshd storage ro|rw|off`で行う。FATには原子的な排他的新規作成を追加し、既存ファイルを誤って切り詰めない。M5FS・devfsの未対応EXCLは明示的に拒否する。

Linux側の単体Pythonヘルパー`tools/tab5_storage.py`はPython標準ライブラリとOpenSSHを使う。`connect HOST ROOT MOUNTPOINT`で既存のSSHFS・FUSEを試し、利用できなければ対話的なSFTPファイル転送へ切り替える。個別の一覧・取得・送信・ディレクトリ作成・削除も用意する。マウントは読み取り専用が既定で、書き込みには`--rw`が必要。SSHの通常のホスト鍵検証・認証を維持し、自動インストールやsudoは実行しない。詳細は[ヘルパー仕様](docs/STORAGE_HELPER.md)を参照。

- ホスト上で実SFTPエンジン、FATアダプター、断片化された通信、排他的作成、部分転送と失敗時の後始末を検証し、全体ターゲットビルドに成功した。実機ではローカルSFTPエンジンを通じ、`/sd/sftp_00ddb817.bin`への新規8192バイトの書込み・読戻し、既存EXCL拒否と再読込みでの内容保持を確認した。この試験にSSH通信・認証は含まない。その後、Wi-Fi実機へParamikoとヘルパーのSFTPクライアントクラスで102400バイトのSD往復を2回実行し、既存EXCL拒否と内容保持、削除・再接続、ROルート一覧・書込み拒否を確認した。認証前にシリアルのSHA256ホスト鍵指紋を照合した。実際の`tools/tab5_storage.py`とWindows OpenSSH 9でも、SDの20480バイトput/get一致、ls/rmを確認した。ユーザーSSH設定は変更せず、シリアル指紋と照合した隔離known_hostsを使用した。Linux上の実プロセス・FUSEマウント、USB媒体のネットワーク転送は未確認。
- 初期接続はLinuxからTab5のSSHサーバーへ到達できることが前提。Tab5から接続したSSH先へ逆方向に公開する方式は未実装であり、今後の項目とする。
- 現在のSSHサーバーは受信1接続のみ。マウント中に別のSSHシェルや転送を併用できない。Tab5のローカルコンソールは利用できる。独立チャネル・同時アクセスは今後拡張する。
- 名前変更・任意の切り詰め・未対応属性などの要求は明示的に失敗させる。書き込み可能なマウントでも、エディタの一時ファイル置換方式などは動作しない場合がある。既存ファイルへの送信は`--overwrite`を明示し、サーバーが操作をサポートする場合だけ実行する。
- 媒体未挿入・取り外し、SSH切断、再接続、アンマウント、同時アクセス時の整合性と連続転送を実機検証する。関連する画像転送・Tab5上での表示は今後の予定。

### MicroPythonとGPIO操作

MicroPython v1.26.1の初期ネイティブポートを実装し、MeOSのタスク・メモリ管理・コンソール・VFSへ接続した。ESP32向けFreeRTOSポートやWASMは使わない。REPL、ファイル実行と`python -c`、512 KiBのPSRAM GCヒープ、32 KiBの専用タスクスタックを用意する。全体ビルドと実機書込みに成功し、REPLで`2**80`、`math.sqrt(9)`とGCを確認した。入力のみの`smoke.py`でGPIO16、ADC16/53、予約ピン・重複・解放済みオブジェクトの拒否と40回GC負荷試験に成功した。SD上の`/sd/mpqa_6adb51fa.py`で隣接モジュールのimport（値123）と、排他的に新規作成した1024バイトのバイナリファイルの書込み・読戻し・seek/tell・末尾24バイト読取・context管理closeに成功した。意図的RuntimeErrorでPin16を残して終了した後の次VMでの再確保、1 MiB bytearrayのMemoryError後の次VM起動、無限ループのCtrl-C中断とシェル復帰・次VM実行も確認した。初期機能の限定検証であり、長時間運用は未評価。外部出力・波形は未確認。初期版ファームウェアは1,396,080バイトで、直前のSFTP版比165,280バイト増加した。周辺IO・time拡張版は1,402,544バイト（初期版比6464バイト増）となった。実機timeの範囲・wrap・delay試験と、60秒sleepのCtrl-C復帰（約0.125秒）を確認した。仕様と制約は[MicroPython実装記録](docs/MICROPYTHON.md)を参照。

### USBスタックの選択（2026-10-23）

M5Stack公式UserDemoはESP-IDFのUSB Host LibraryとHIDドライバーをFreeRTOSタスクから利用している。Tab5thinclientはTinyUSBのHID・MSC Host APIを利用する。本フォークは独自ディスクリプタDMAドライバへ集約する。TinyUSB 0.19.0を参照し、ホストモード切り替え完了を待ってからFIFOを設定するよう独自HALを修正した。修正版でUSBメモリの読み書きと再起動後保持を確認。PHYの電源・クロックとDWC2 HALにはESP-IDFを使用し、FreeRTOSスケジューラーは使わない。TinyUSBのOS_NONE・FIFO版は比較用に残す。実装と検証範囲は[USB実装記録](docs/USB_IMPLEMENTATION.md)、[DMA調査記録](docs/USB_DMA_INVESTIGATION.md)を参照。

## 資源使用量の比較

基準の上流MeOSと現在版のBIN・静的HP SRAM・内部ヒープ予約領域を、同一sdkconfigハッシュ・ESP-IDF・コンパイラによる再ビルド結果から比較する。数値は`docs/resources/baseline.json`、`current.json`、`comparison.json`から公開ページへ生成する。基準版に必要な宣言のみのビルド修正と、各成果物のハッシュは[資源使用量の記録](docs/RESOURCE_USAGE.md)を参照。

静的HP SRAMには内部ヒープの予約領域全体を含むため、実行時の内部ヒープ使用量を加算して総RAM使用量とはしない。PSRAM、タスクスタック、アプリの実行時使用量はワークロード依存であり、異なる時点の値を機能追加の単独コストとして差し引かない。
