# Tab5 MeOS FPGA — 開発目的と開始記録

更新日：2026-10-23

## 目的と範囲

主目標を、FPGAによる描画支援を組み込んだMeOSのGUI化とする。Tab5上で、ウィンドウ、メニュー、文字、画像を扱うGUIを構築し、Tang Primer 20Kとその128MB DDR3を描画処理・画像資源の保持に活用する。文字中心の操作環境から、初期Windowsのようなウィンドウ操作環境への発展を目指す。Windows互換性は要件に含めない。

MeOS側は入力、ウィンドウ管理、アプリの状態、描画命令の生成を担当し、FPGA側は矩形塗りつぶし、画像コピー、合成などを段階的に担当する。具体的な分担は転送時間を含む測定で決める。既存の上流GUI・コンソール・表示ドライバを調査し、利用できる部分を土台にする。

大容量データの分割処理、明示的な退避・復元、演算アクセラレーションは、GUI基盤と共通する転送・バッファ管理を活用する副次的な研究対象とする。

Linux版とMeOS版を別リポジトリで管理し、通信プロトコル、データ照合、評価条件を整合させる。OSごとのAPI・メモリ管理・スケジューラ・DMA対応は個別に調査する。Linux用ドライバをそのまま利用できるとは扱わない。

FPGA側DDR3は明示的に転送する外部データ領域であり、通常のCPUポインタで参照できる主記憶や透過的なmalloc領域とは扱わない。GPU用と外部RAM用の同時搭載は初期の要件とせず、資源・帯域の評価後に判断する。

## GUI化の段階と評価

1. **基準環境**：MeOSのTab5向けビルドと表示経路を確認し、CPU描画の所要時間と内部RAM・PSRAM使用量を記録する。
2. **通信とDDR3**：小さなデータの往復照合から開始し、転送の安定性・実効帯域・DDR3のデータ保持を確認する。
3. **最小描画支援**：FPGA側バッファへの矩形塗りつぶしと画像コピーを実装し、Tab5画面に結果を表示する。命令送信・実行・画像回収・表示を含む所要時間をCPU描画と比較する。
4. **GUI統合**：MeOSの描画APIにCPU実装とFPGA実装の切替を設け、ウィンドウの表示・移動、メニュー、文字・画像表示を検証する。画像資源の常駐と変更領域の転送を評価する。
5. **拡張**：測定結果に応じて合成、拡大縮小、追加の計算処理へ進む。

最初の到達点は、Tab5で入力操作できるウィンドウとメニューを表示し、少なくとも一つの描画処理をFPGA経由で実行できることとする。高速化の成立は別途測定で判断し、フレームレート、操作応答時間、CPU負荷、RAM使用量、転送量を記録する。

初期はTab5既存LCDへのESP32-P4経由の表示を評価する。FPGA側DDR3に画像を置いても、表示のための画像回収が帯域を消費するため、表示経路は設計上の主要な検証項目とする。FPGAからの直接表示は別途ハードウェア構成の検討が必要であり、初期の前提にしない。

### USB対応後のSSHサーバーと同時実行

USBホストの汎用化とmicroSD対応に続いて、SSHサーバーを実装する。PCからMeOSへログインし、シェル操作、ファイル転送、アプリの配置・実行・診断を行える開発経路を用意する。既存のSSHクライアントと同時実行し、サーバー側の接続を維持したままクライアントの接続・通信・終了・再接続をSSH経由でテストできることを到達条件とする。

接続ごとの入出力・シェル状態・資源所有権を分離し、LCD／シリアル／SSH間の入力競合を解消する。サーバーのホスト鍵・利用者認証、接続数・バッファ上限、切断時の資源解放、ネットワークソケットの同時使用を設計する。認証なし・暗号検証省略のサーバーにはしない。現時点では計画であり未実装。

### SSH対応後のタッチ操作

実施順はUSB受信機・USBメモリ、microSD、USB書き込み修正とハブ・複数機器対応、SSHサーバーと既存クライアントの同時動作、タッチ対応、Bluetoothキーボード・マウス対応とする。接続端末のST7123を対象に入力ドライバーを追加し、上下スワイプでコンソールのスクロールバックを操作できるようにする。画面の自動スクロールとは区別し、過去出力の保持、表示位置、最新出力への復帰、出力継続中の閲覧、画面キーボードとの入力判定を設計する。ローカルとSSH用端末の双方で利用できる共通入力経路を検討する。

### SSH接続先からのストレージマウント（詳細）

Tab5_thinclientのサーバー側FUSEヘルパーとSSH通信方式を参考に、Tab5から接続したLinuxサーバー上で、Tab5のmicroSDを`~/sd`、USBメモリを`~/usb`などにマウントする。サーバー上のエディタやコマンドからファイルを直接読み書きできることを目標とする。MeOS自身にLinuxやFUSEを移植する方式ではなく、サーバー側ヘルパーとMeOS側VFS操作をSSH経由でつなぐ。

- 初期はLinuxサーバーを対象とし、Python・FUSE・ユーザーマウントの利用条件を確認する。既存ヘルパーの互換性と再利用条件を調査する。
- SSH端末用とは別のチャネルで、一覧取得、属性取得、ファイルの読み書き・作成・切り詰め・名前変更・削除、ディレクトリ操作を扱う。
- 公開する領域をmicroSD・USBメモリの指定ルートに限定し、範囲外のパスを拒否する。読み取り専用と読み書きを選択できるようにする。
- ローカルのファイラー・アプリとの同時アクセス、キャッシュ整合性、書き込み完了・同期を設計する。切断時に未完了の書き込みを成功として扱わない。
- 媒体未挿入、取り外し、SSH切断・再接続、サーバーヘルパー終了時のエラー通知とマウント解除を整備する。
- 小さなファイルの読み取りから開始し、書き込み、ファイル操作、同時アクセスへ拡張する。転送前後の内容照合と切断試験で確認する。
- 関連機能としてSCP相当のファイル転送、サーバー上の画像をTab5へ転送・表示する機能も実装予定に含める。

### MicroPythonとGPIO操作

MicroPythonをMeOSのタスク・メモリ管理・コンソール・VFSへ接続する。既存のESP32向けポートやTab5_thinclientの実装は依存関係を調べて参考にし、FreeRTOS依存の実装をそのまま利用できるとは扱わない。REPLとスクリプト実行を入口とし、Ctrl-Cによる中断、例外表示、終了時の資源解放、GCヒープとタスクスタックの使用量を検証する。

GPIO操作はMeOS側に共通の管理APIを設け、MicroPythonとネイティブシェルの両方から利用する。最初はデジタル入出力とプル設定を対象とし、PWM、ADC、割り込み、I2C・SPIなどは対応ピン・周辺回路と依存関係を調査して段階的に拡張する。

- Tab5の外部端子とGPIO番号の対応、対応する入力・出力モード、予約用途、使用中の所有者を一覧化する。
- LCD、PSRAM、Wi-Fi、ストレージ、キーボード、FPGA通信などの使用ピンを管理し、競合する再設定を拒否する。
- シェルのコマンド案は`gpio list`、`gpio mode <pin> <in|out> [none|up|down]`、`gpio read <pin>`、`gpio write <pin> <0|1>`、`gpio release <pin>`とする。最終構文は既存CLIとの整合を確認して決める。
- MicroPythonは`machine.Pin`の基本操作との互換を目指す。ピン確保・解放と、スクリプト終了・例外・中断時に出力状態をどう扱うかを明文化する。シェルの設定は明示的な解放または再起動までの扱いを定める。
- 利用可能な端子で入力・出力・プル設定、無効ピン指定、所有権競合、中断後の再実行を確認する。外部接続前に電圧・配線条件を確認する。

### CPython・Pyxelによる既存ゲームの実行

公開されているPyxelゲームのPythonソースと素材を、作品ごとのC/C++化やWASM化、素材の事前変換なしでMeOS上へ取り込んで実行することを目標とする。CPythonとPyxel本体の移植を第一候補とし、MicroPythonによる互換APIの再実装とは別の開発項目として扱う。任意の作品への完全互換や快適な速度は、現時点では保証しない。

- 対象のCPython・Pyxelの版を固定し、Pythonバインディング、Rustの標準ライブラリ・ターゲット対応、SDL2・OpenGLなどの依存関係を調査する。MeOS上でのネイティブ実行を基本候補とし、既存のブラウザー向けWASMをそのまま利用できるとは扱わない。
- CPythonに必要なメモリ管理、ファイル、時刻などをMeOSへ接続し、Pyxelの画面・入力・音声・ファイル処理のプラットフォーム依存部分を移植する。ゲームのPython処理と、エンジンのネイティブ処理を区別する。
- 最初は公式のJump Game、次にPlatformerを対象に、元のPythonソースと`.pyxres`を使った読み込み・実行を検証する。キー状態と押下イベント、透過色、反転、カメラ、タイルマップ、画像バンクの変更、文字、乱数、音楽・効果音を段階的に確認する。
- 32MB PSRAMと内部RAMの制約に対し、CPython、Pyxel、素材、画面、音声の使用量と起動時・実行時のピークを測定する。FPGA側DDR3は明示転送するバッファとして活用し、CPythonの通常ヒープが自動的に拡張されるとは扱わない。
- 互換性の成立をCPU描画で先に確認し、描画経路へFPGA支援を追加する。元の論理解像度で処理し、拡大表示、画像コピー、合成などの分担を評価する。
- 同じ入力によるPC版との画面・状態比較、音声・入力の確認、フレーム時間・応答時間・RAM使用量の測定で評価する。対象作品の元の更新周期を維持することを性能目標とし、互換性と高速化の結果を分けて記録する。
- 外部PythonライブラリやOS機能への依存、Pyxelの版差、作品と素材の利用・再配布条件を確認し、対応範囲を作品ごとに記録する。

参考実装：[Pyxel](https://github.com/kitao/pyxel)、[Jump Game](https://github.com/kitao/pyxel/blob/main/python/pyxel/examples/02_jump_game.py)、[Platformer](https://github.com/kitao/pyxel/blob/main/python/pyxel/examples/10_platformer.py)。

### 優先順

基準ビルド・実機確認の後、入力統合とmicroSD・FAT対応をGUI・FPGA通信の研究と並行して進める。ストレージマウントはmicroSDで読み取りから検証し、書き込みとUSBメモリへ広げる。GPIOの共通管理とシェル操作を整えた上で、MicroPythonのREPL・スクリプト実行とGPIO APIを統合する。USBマウス、端末共通化、Bluetooth入力、追加アプリ移植は依存機能の成立に合わせて進める。具体的な性能目標と日程は測定・実機確認後に定める。

## メモリ削減の検討案：日本語フォントの外部化

日本語フォントをmicroSDへ保存し、起動時にFPGA側DDR3のフォント用領域へ読み込む案を検討する。現時点では採用・実装済みではなく、Tab5のmicroSD対応とFPGA通信・DDR3利用の成立が前提となる。

- 現在の埋め込みフォント配列は467,155 bytes（約456KiB）で、フラッシュから外すことによる容量削減を見込む。フラッシュ配置のため、外部化だけで同量の内部RAMが空くわけではない。
- CPU描画では、必要な字形をFPGAから取得し、Tab5側へキャッシュする。既存の約9KiBの字形キャッシュを活用・調整し、文字ごとの転送待ち、索引、圧縮データへのアクセス方法を評価する。
- FPGA描画ではDDR3上のフォントを直接参照する構成を検討する。データ領域として管理するだけならRAMディスクのファイルシステムは必須ではない。RAMディスク方式との選択は共通ストレージ設計に合わせて判断する。
- 起動メッセージとエラー表示用の小さな英数字フォントは本体に残す。SD未挿入、フォント不正、FPGA初期化失敗時の代替表示と診断を用意する。
- 元のフォントとライセンス表示を保持し、データ形式・版・長さ・整合性を確認して読み込む。起動時間、キャッシュヒット率、文字描画時間、フラッシュ・RAM削減量を測定する。

### USBハブ・複数機器対応

USBハブを介した複数のUSBメモリ、およびキーボードとUSBメモリの同時利用を実装対象とする。現状は直結1台のみであり、未対応。ハブのポート電源・接続変化・リセット・アドレス割り当て、機器別エンドポイントとDATA PID管理、複数MSCインスタンスと独立したVFSマウント、切断時のハンドル処理を追加する。High-Speedハブ配下のFull/Low-Speed機器にはスプリットトランザクション対応が必要で、検証対象に含める。複数メモリ間の読み書きとキーボード入力の継続、個別取り外し・再接続で他機器を妨げないことを確認する。

### USBスタックの選択（2026-10-23）

M5Stack公式UserDemoはESP-IDFのUSB Host LibraryとHIDドライバーをFreeRTOSタスクから利用している。Tab5thinclientはTinyUSBのHID・MSC Host APIを利用する。MeOSではTinyUSB 0.19.0のOS_NONE構成を採用し、MeOS mutexとタスクによるポーリングへ接続した。PHYの電源・クロック初期化はESP-IDFに残し、USB列挙・転送・BOT・HIDをTinyUSBへ任せる。現在はDWC2 FIFO方式を使用し、DMAは無効。元の独自実装の停止原因そのものは未確定であり、DMAが原因と断定するものではない。実装と検証範囲は[USB実装記録](docs/USB_IMPLEMENTATION.md)を参照。
