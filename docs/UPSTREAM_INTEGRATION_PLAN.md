## 上流を取り込む手順

### 基準を保存する

- 現在のコード、SDK、ビルド設定、書き込み済みファームウェアとアプリのハッシュ、FPGAイメージ識別情報を保存する。過去の試験結果は対象ハッシュと組にして保持する。
- carrierリポジトリのremoteを確認し、仕様、最終ピン割り当て、生成ハードウェア、監査記録との差分を調べる。参照SHAと変更点を [FPGA_CARRIER_REQUIREMENTS.md](FPGA_CARRIER_REQUIREMENTS.md) に記録してから実装する。
- `codex/merge-upstream-20261105` のような統合専用ブランチを作り、必要なら別worktreeを使う。新規worktreeは `D:\github\airpocket-soundman` 配下に置き、既存のdirty checkoutは保持する。

### 競合を依存順に解消する

1. **ビルドとボード設定**：CMake、機能選択、ボード定義を統合する。上流のCardputer対応終了を反映し、モジュール定義にも不要な対応ボードを残さない。標準構成とFPGA用構成を区別する。
2. **カーネル**：スタック診断を既存のFPU保存・初期コンテキストと合わせる。フレームサイズ、アラインメント、ガード、タスク終了・再利用を確認する。
3. **I2Cとボード操作**：上流の起動時復旧と、こちらの固定システムバス・排他制御を統合する。キーボードのバス選択でシステム機器の宛先が変わらないようにする。
4. **入力**：上流のタッチスナップショット、キーボード呼び出し、復帰入力と、こちらのIME排他・入力フォーカスを統合する。終了済み所有者の回収と既存状態の復元を保つ。
5. **表示**：キーボード領域の描画クリップ・描画停止と、こちらの描画バッチ・バッファ所有権・実DMAアドレスによる完了確認を統合する。ST7123初期化とM5EX向け表示APIも維持する。
6. **シェルとアプリ**：コマンド登録、カメラ、画像ビューア、SSH/Webの再描画を統合する。上流とこちらの画像読み込み処理を重複して残さない。

競合ファイル全体を機械的に片側採用しない。特に `display_tab5.c`、`kprintf.c`、`i2c_bitbang.c`、`main/CMakeLists.txt`、`shell.c` は双方の契約を確認する。

### サスペンドをFPGA利用と連動させる

上流は既定で無操作180秒後にサスペンドし、拡張5VをOFF、CPUを90MHzへ変更する。この動作をFPGA通信・周辺機器の利用と調整する。

- 初回の統合検証ではFPGA用構成の自動サスペンドを無効にする。上流のサスペンド機能そのものは削除しない。
- 通信やDMAなど、停止・電源変更に対応できていない機能が資源を所有している間はサスペンドを抑止する。手動要求にもBUSYと理由を返す方針で設計する。
- 画面を暗くすること、描画を止めること、拡張電源を切ることを区別する。どの電源がFPGAへ影響するかはcarrierの配線・給電仕様から確認する。
- 復帰時にクロック、GPIO方向、描画状態、入力フォーカスを確認する。通信失敗後の無条件再送や、CPU描画への暗黙の置き換えは追加しない。
- 共通のサスペンド抑止APIと対象範囲は実装時に決める。自動サスペンドの無効化だけで恒久対応済みとは扱わない。

### Tailscale設定ファイルによる起動時接続

A6は新規実装する計画であり、現在の「起動時はdown」という実装から変更する。`autoconnect` フラグは追加せず、明示した設定ファイルの存在を自動接続の有効化条件にする。

| 起動時の状態 | 動作 |
| --- | --- |
| 設定ファイルなし | 自動接続しない。手動の `tailscale up` を利用できる |
| 設定ファイルあり、内容が有効、利用可能な登録情報あり | 保存した端末情報で接続を開始する |
| 設定ファイルあり、内容が有効、認証・登録が未完了 | 対応する初回認証フローまたは認証が必要な状態を明示する。接続済みとは表示しない |
| 空、不正、読み取り失敗 | 自動接続しない。秘密情報を含めず理由を表示し、暗黙に既定設定で接続しない |

- 自動接続の判断はOS起動ごとに一度行う。永続ストレージの準備後に読み込む。シェルやGUIを開き直しても自動接続をやり直さない。
- `tailscale up/down` は現在の接続状態を変更し、設定ファイルを書き換えない。down後はその起動中の自動再接続を止め、古い応答も破棄する。設定ファイルが残っていれば次回起動時に再び判断する。
- ファイルがなくても、手動upのために保存済みの端末情報は利用できる。端末情報が保存されているだけでは自動接続しない。
- ネットワーク準備待ち・一時切断後の再試行には間隔・中断条件を設け、downによって中止できるようにする。
- 通常設定と秘密情報を区別する。必要に応じてホスト名・接続先などを設定し、端末の鍵・登録状態は再起動後も読み戻せる形で保存する。Auth Keyによる登録とブラウザ認証の扱いを明記し、秘密鍵・Auth Keyを通常の設定表示やログへ出さない。
- 保存先、ファイル形式、必須項目、端末情報の保存方法、初回認証の具体的な操作は実装前に確定する。RAM上のファイルだけで永続化済みとは扱わず、設定をシステムが自動作成して意図せず接続を有効化しない。

試験には、ファイルの有無・破損・読み取り失敗、登録済み情報の再読込、初回認証、ネットワーク遅延、シェル再起動、down後に遅れて届く応答、次回OS起動での再判定を含める。旧挙動と試験結果は [TAILSCALE_DOWN_2026-10-26.md](TAILSCALE_DOWN_2026-10-26.md) を履歴として残す。

## FPGA関連のPR

FPGAのRTL、制約、ビットストリーム、コマンド仕様はcarrierリポジトリが所有する。MeOSではホスト実装、API、診断、アプリを提出する。各機能は原則として既定OFFとし、物理通信を明示的に有効化する。

| ID | 提出する機能 | 前提と検証 |
| --- | --- | --- |
| F1 | LINKホストと診断 | B4、必要ならB3。ID、echo、CRC、ピン所有権、carrier参照SHA、明示的な有効化 |
| F2 | PARLIO/GDMA通信 | F1。DMA所有権、時間上限、キャンセル、異常停止時の資源保持、検証済み速度 |
| F3 | GFXホストAPIと読み戻し検証 | 対応するF1/F2とビットストリーム。描画命令、厳密な応答検証、画素比較 |
| F4 | フラクタル計算API | F2と対応するビットストリーム。専用演算呼び出し、フレーム単位セッション、所有者終了 |
| F5 | CPU/FPGAフラクタルアプリ | F4、B2、B8。状態表示、アニメーション、同一条件での比較、終了後回収 |

旧GFX命令とE368のTILE/batch系など、必要なイメージを機能ごとに明記する。NPU/MEMはCPU上の模擬検証、ホスト実装、FPGA実機試験を区別し、物理仕様と対応イメージの到達点を確認して別PRにする。専用アクセラレータはGFX/GPGPUへ発展させる検証過程として位置づける。

## PRを作成する手順と提出順

1. 上流マージを検証して、このフォークの基準版を更新する。
2. A1〜A5の独立修正から抽出する。A6は本書の設定ファイル仕様を実装・検証してから提出する。
3. B1/B2の表示・入力基盤とB4〜B6のI/O基盤を進める。B3のモジュール機構は上流の機能選択方針を確認して提出する。
4. C群を依存順に提出する。大規模な第三者コードと共通基盤変更を一つのPRへ混ぜない。
5. B7/B8を経てF群を提出する。上流が拡張ハードウェア対応を希望しない場合、共通基盤だけを上流へ戻し、F群はこのフォークで維持する。

提出用ブランチは、その時点の上流mainを基に `codex/pr-<feature>` として作る。`bcaf737` や `8e9935b` の複数機能を含むコミットは、そのままcherry-pickせず、必要なコード・試験・説明だけを抽出する。依存PRが未採用なら依存先を明記し、採用後にrebaseして差分を縮める。

各PRは、解決する問題、変更後の動作、対象ボード・SDK、対応試験、実機確認範囲、残る制約を記載する。標準のビルドを維持し、必要な機能は明示的に選択する。試験記録は機密情報を除き、対象コミットと成果物ハッシュに結び付ける。計画の保存・更新だけでは、実際のマージ、PR公開、実機書き換えを実施したことにはしない。
