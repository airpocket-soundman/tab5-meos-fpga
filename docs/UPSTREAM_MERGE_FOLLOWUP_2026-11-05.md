# 上流マージ追加試験（2026-11-05）

前回記録: [UPSTREAM_MERGE_TEST_2026-11-05.md](UPSTREAM_MERGE_TEST_2026-11-05.md)。
統合ブランチ `codex/merge-upstream-20261105` で試験を継続した。mainは変更していない。
使用機体はこのセッション用COM22 / USB識別子 `E8:F6:0A:E3:21:CF`。
別セッションのTab5・FPGAにはアクセスしていない。

## 今回見つかった問題と修正

`f840963`で `sshd start` を実行すると、SDK5.5.2の
`regi2c_enable_block()` が `regi2c_ctrl_ll_master_is_clock_enabled()` のassertで再起動した。

1. 乱数初期化が、停止中の内部アナログI2Cマスタークロックを使ってADCの旧設定を読んでいた。
2. 読出し前のクロック有効化だけでは不十分だった。`esp_fill_random()` が呼ぶAPBクロック取得は、
   CPLL設定をSDKのREGI2Cラッパーで読み、その参照カウントを解放するとクロックを再停止する。
   その後のADC復元書込みでも同じassertが起きた（`09a5cfe`の実機確認）。
3. `089ddb3`では初回読出し前と乱数取得後にクロックを有効化し、最後のADC復元後に
   共有クロック・電源・ADC設定を元の状態へ戻す。
4. GPIOのネイティブADC処理にも、ROMアクセス前のクロック有効化を追加した。
   こちらのSDK呼出し経路には途中でクロックを停止する処理がないことをソースで確認した。

当該乱数処理は基準 `fab6f83` と最初の統合版 `f840963` で同一だった。
上流マージ固有の回帰とは断定せず、追加試験で判明したSDK互換性の問題として記録する。

修正のホスト試験は実際のソースを使用する。
内部I2Cクロック・電源の前提条件、初期ON/OFF、成功・タイムアウト、状態復元、IRQ保護、
乱数取得中のSDKによるクロック停止を再現した。修正を除いた負の対照が失敗することも確認した。
ADCは両ユニット×成功/タイムアウト/異常値×初期クロックON/OFFの12条件に合格。
これは実電圧・ADC精度の検証ではない。

## 追加の実機確認

### タッチ

ユーザー操作でコンソールを上下にスクロールできたとの回答を受領。
この確認は前の統合版f840963で実施。今回の修正ではタッチ/表示の実装を変更していない。
OSK・実キーボード・IMEの全操作を確認したという意味ではない。

### SSHサーバーとSFTP（Wi-Fi、実SD）

実機の公開ホスト鍵のSHA256をシリアルで取得し、テスト側のSSHクライアントで照合した。
一時アカウントを使用し、既存のSSHサーバーが停止していることを確認してから開始。

- 間違ったパスワードを拒否、正しいパスワードで認証成功。
- SSHの共有コンソールから `echo MERGE_SSH_PASS` が実行できた。
- SFTPで `/sd` 内の新規・一意なファイルを排他的に作成し、8,192 bytesを書込み・読み戻し。
- SHA256 `dc404a613fedaeb54034514bc6505f56b933caa5250299ba7d094377a51caa46` が一致。
- 同名の排他的作成を拒否し、既存内容が維持されることを確認。
- サーバーを停止して読取り専用へ切り替え、同じファイルの読取りに成功。
  書込み要求は拒否され、内容が維持された。
- 終了後はSSHサーバーを停止し、ストレージ公開方針を読取り専用へ戻した。
  テストファイルは削除。認証情報・ホスト鍵の秘密部分をレポートへ記録していない。

### SSHサーバー／クライアント同時動作

PCからTab5へSSH接続した状態で、その共有コンソールからTab5のSSHクライアントを実行。
PC上の一時的な別SSHテストサーバーへ接続し、パスワード認証とexec要求に成功。
緑色ANSI表示を含む `MERGE_CLIENT_OK` を受信し、クライアント終了後のプロンプトを待ってから、
元のSSH接続で `echo NESTED_DONE` を実行できた。

PCのテストサーバーは受信コマンドをOSで実行せず、固定の応答だけを返す。
終了時にリスナーを閉じた。ファイアウォール設定・既存SSHサービスは変更していない。

### SSH/SFTPホスト相互接続試験

実際のプロトコル・暗号コードを使う32bit Windowsモデルに対して、
`tests/ssh/run_protocol_test.py` が成功。14接続ケースとパケット境界試験を実施。
正しい/誤った認証、exec拒否、不正パケット、192KiB転送、短いI/O、排他的作成、
ポータブルヘルパー、読取り専用、パス制限、フレーム不正、EOF/CLOSE、公開無効を確認した。
環境はZig0.13、Paramiko5.1.0。ホスト試験の乱数は試験用であり、実機の乱数初期化確認とは分けている。

## 資源の観測

内部ヒープ使用量はSSH停止後92,592 bytesへ戻った。スタックガードは全タスクOK。
PSRAMは初回TCP利用でソケットごとの受信バッファを保持する仕様だった。
`drivers/wifi/wifi_tab5.c` の `TCP_RX_BUF_SIZE=65536` と、初回割当て・再利用処理を確認。

- TCP未使用時: 8,588,864 B
- SSHサーバー用ソケットを初めて使用した後: 8,654,416 B（+65,552 B）
- クライアント用ソケットも使用した後: 8,719,968 B（合計+131,104 B）

増分は2個の64KiB受信バッファとアロケータの管理領域に一致した。
接続・切断を繰り返しても同じ値で、セッション・SFTP・タスクの割当ては回収された。
この2バッファは停止時にも保持する現在の仕様として記録し、使用量ゼロ増とは扱わない。
SDK側ヒープ全体やチップ全RAMの観測ではない。

## 修正後の基本動作再試験

同じ089ddb3でMicroPython、ACK付き画像転送、BMP情報取得、BMP/PPM/既存ビューア各3回、
ローカルSDの新規9 bytes書込み・別openでの読み戻し・削除を再実行した。
TCPバッファが2個確保された状態で、開始前・各反復後・終了後の5回すべてが
内部92,592 B / PSRAM8,719,968 Bで一致。割当て失敗0。
最終描画はsubmitted=retired=129、errors=0、timeouts=0、全対象スタックガードOK。
テスト画像とSDの一時ファイルは削除した。

実機のSSH応答はLFを含むため、試験器でCRLFだけを前提にせず正規化した。
入れ子のSSH試験では、接続開始時の古いプロンプトと、exec完了後の新しいプロンプトを区別して待つようにした。
これらの試験器の修正は、実機を再起動させたSDKクロック制御の不具合とは分けて記録する。
