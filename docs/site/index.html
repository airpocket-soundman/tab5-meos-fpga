Tab5 MeOS FPGA Development Plan

Plan to add Tang Primer 20K rendering operations and external DDR3 buffers to MeOS on M5Stack Tab5. This document describes implementation status, architecture and validation requirements.

Core hardware checks passed for baseline firmware, FP context, microSD, USB Ethernet, Wi-Fi, concurrent SSH, touch scrolling and the built-in camera. USB storage regression on the new transfer engine remains pending. USB cameras and Bluetooth passed limited checks; full input/video validation remains pending. FPGA and GUI extensions are planned.

Updated: 2026-10-24

Development order and progress

Core hardware checks complete: 11 items / Implemented, awaiting regression: 2 items / Partly implemented, host-tested: 1 / In development: 4

Complete means the documented core hardware checks passed. Stress tests and additional features remain separate follow-ups. USB features affected by the transfer-engine change are marked as awaiting regression checks.

  1. Baseline firmwareComplete: core hardware checks passed

    Size-optimized firmware flashed; boot, mem, ps and ls verified. Full regression pending.

  2. OS foundation: floating-point contextComplete: core hardware checks passed

    ESP32-P4 cooperative switches preserve FP callee registers and FCSR; timer interrupts preserve all FP registers and FCSR. Hardware task-isolation and host layout/initialization tests passed. This is not exhaustive instruction or ISR validation.

  3. 1. USB receivers and storageImplemented: regression checks pending

    Native DMA verified: 37, 512 and 8192 byte write/read and persistence. Reconnection corrected; one idle unplug/replug cycle passed remount, full original-file readback and a new 512-byte write/read. TinyUSB retained for comparison. Receiver input passed both directly and through a High-Speed hub. Storage write/read regression after the Buffer DMA conversion remains pending.

  4. 2. microSDComplete: core hardware checks passed

    Verified on hardware: SPI access, /sd FAT mount, listing, 38-byte test file write/read and persistence after reset, simultaneous /usb mount. Speed optimization and hot-plug unverified.

  5. 3. USB hubs, multiple drives and keyboard coexistenceImplemented: regression checks pending

    Unified the native host on Buffer DMA and added split transfers for a Full-Speed wireless receiver beneath a High-Speed hub. Reports and shell commands were verified in logs and by the user; two drives mounted and Ethernet ping passed 10/10. Diagnostics removed. New-engine write/read coexistence remains unverified because USB devices were absent during the attempt. Earlier CRC write/read results apply to the previous engine.

  6. 3a. USB EthernetComplete: core hardware checks passed

    RTL8153 CDC-ECM passed hardware link, DHCP, ping and SSH. Releasing the USB lock during MSC DMA waits enabled reads/writes on both drives alongside 20/20 ping replies per test with zero USB errors or drops. Long-duration and hot-plug continuity tests remain pending.

  7. 3b. Wi-Fi validationComplete: core hardware checks passed

    Updated C6 over SDIO to the official MCU application. Reset persistence, Wi-Fi initialization, scanning, WPA2 association and DHCP passed. With Ethernet unplugged and inactive, Wi-Fi DNS resolution and HTTP 200 retrieval passed on hardware. Long-duration traffic and reconnect tests remain pending.

  8. 4. Concurrent SSH server and clientComplete: core hardware checks passed

    Shared-console SSH server implemented. Hardware authentication, commands, reconnect, stop and outbound SSH while keeping inbound SSH active passed. TCP slots are separate from Web/Tailscale. The SFTP extension passed host tests and the complete target build. Independent PTYs and exec are not implemented; see item 4b for SFTP validation scope.

  9. 4a. Shared terminal: VT100 / VT220 / xtermPartly implemented: host tests passed

    LCD/SSH implement 256/RGB colors, scroll margins, line edits, cursor save/restore and alternate screens. SSH adds DSR, DECCKM and Vim key passthrough. Actual-parser host tests passed; SL passed hardware serial ANSI completion and interrupted return. Device Vim checks, visual SL assessment and full VT220/xterm compatibility remain pending.

  10. 4b. SFTP and Linux storage helperComplete: core hardware checks passed

    Implemented the SFTP v3 engine, SD/USB export boundaries, read-only default policy and atomic FAT exclusive creation. A standalone Python standard-library/OpenSSH helper uses connect to try existing SSHFS/FUSE, falling back to interactive file transfer. Host tests and the complete target build passed. The local SFTP engine passed an SD hardware self-test: fresh 8192-byte write/read, refusal of existing-file EXCL and unchanged contents on reread. Over hardware Wi-Fi, Paramiko and the actual helper SFTP client class passed two 102400-byte SD roundtrips, existing-file EXCL/content preservation, delete/reconnect, and read-only listing/write rejection. The serial SHA256 host-key fingerprint was checked before authentication. The actual helper process with Windows OpenSSH 9 also passed an exact 20480-byte SD put/get and ls/rm using fingerprint-verified isolated known_hosts without changing user SSH settings. Actual Linux process/FUSE tests and USB network transfers remain unverified. Only one inbound connection is supported; reverse export through Tab5-initiated SSH is not implemented.

  11. 5. Touch and console scrollingComplete: core hardware checks passed

    256-line colored history, vertical swipes and return to live output implemented. The user confirmed scrolling on ST7121. Two-buffer rendering passed 20 updates and 20 DMA-confirmed retirements with zero errors/timeouts. Subjective flicker reduction and long-duration tests remain unverified. With UVC active, display retirement passed 16/16 with zero errors, but maximum batch time reached 1.642 seconds; high-load response latency remains.

  12. 6. Bluetooth keyboard and mouseImplementation / device validation

    BLE initialization passed through C6 SDIO HCI (ready, error 0). A 3-second passive scan discovered two nearby devices; HCI TX20/RX22, failed 0/reject 0. No automatic connection was attempted. Paired HID keyboard/mouse input and reconnect remain unverified; Classic requires separate assessment. Wi-Fi HTTP 200 retrieval (577 bytes) also passed after BLE startup and scanning. Current connection management is limited to one peer.

  13. 7. USB cameras (UVC)Implementation / device validation

    The connected UVC camera passed hardware capture of one 160×120 frame and BMP save, using a 2688-byte payload and alternate setting 6 with three High-Speed transactions. Image quality, sustained capture, preview and hot-plug remain unverified. Current acquisition takes about 8–10 seconds per complete frame, with many bad/incomplete payload observations; a practical frame rate has not been achieved. BMP readback found 19113/19200 nonzero pixels with varying values (FNV 9c385858); visual color/orientation/quality checks remain pending.

  14. 8. Tab5 built-in cameraComplete: core hardware checks passed

    Native CSI/ISP RGB565 capture passed on SC202CS (ID eb52). A 640×360 image was saved to microSD as a 460870-byte BMP. Stop/restart and a fresh frame passed with zero DMA errors. Image quality, sustained frame rate and long-duration operation remain unmeasured. BMP readback found all 230400 pixels nonzero with varying values (FNV 07d53fa4).

  15. 9. External GPIO, ADC, PWM, I2C, SPI and UARTImplementation / device validation

    Shared C services and shell control for GPIO, uncalibrated ADC, PWM, SoftI2C/SoftSPI and UART1 are implemented; host tests and the complete target build passed. Hardware checks passed reserved-pin rejection, GPIO16 input/release/reset, raw ADC16/53 sampling and internal UART loopback; ADC35 was rejected as unsupported. External devices, reference voltage, PWM waveforms and wired I2C/SPI/UART remain unverified. See items 10/10a for Python bindings. General-purpose DAC is excluded.

  16. 10. MicroPython and machine.Pin / ADCComplete: core hardware checks passed

    Implemented the initial native MeOS port of MicroPython v1.26.1, REPL/scripts/VFS integration and machine.Pin / ADC. The GC heap uses 512 KiB PSRAM with a 32 KiB task stack. Shared IO ownership and VM-exit file/pin cleanup are provided. The complete target build and flashing passed. Hardware REPL checks passed 2**80, math.sqrt(9) and GC; smoke.py passed GPIO16 input, ADC16/53, reserved/duplicate/released-object rejection and 40 GC pressure cycles. An SD script passed sibling-module import and exclusive 1024-byte file write/read, seek/tell and close. Pin reclaim after an intentional exception, VM restart after MemoryError and Ctrl-C interruption of an infinite loop followed by shell return/new VM execution also passed. These verify the initial feature scope; long-duration operation is unmeasured. External output waveforms remain unverified. See item 10a for PWM/UART/SoftI2C/SoftSPI/time additions. IRQ and CPython/Pyxel compatibility are not included.

  17. 10a. Python peripheral IO and monotonic timeImplementation / device validation

    Implemented PWM, UART1, SoftI2C, SoftSPI and time. The actual 32-bit MicroPython VM with mocked IO passed functional and exception-cleanup tests (156 service calls, eight accepted UART bytes). Hardware passed no-output PWM rejection, UART configuration rejection,23 bus safety checks and time range/wrap/delay tests. Ctrl-C returned from time.sleep(60) in about 0.125 seconds. Firmware grew by 6464 bytes. Physical PWM waveforms, wired UART and real I2C/SPI device communication remain unverified; IRQ is not implemented.

  18. 11. Native SL portComplete: core hardware checks passed

    Ported upstream SL 5.03 with original code/assets/license retained, a minimal MeOS ANSI/curses-shaped adapter and PSRAM canvas/smoke state. More than 90 host runs and full target build/flash passed. On hardware serial, default sl completed in 15.30 seconds with 95329 output bytes, alternate-screen enter/exit and shell return. Ctrl-C during sl -aF and Esc during sl -lc each returned in about 0.86 seconds and reruns passed. Visual quality, LCD appearance and SSH rendering remain unassessed.

Architecture and milestones

MeOS manages input, windows, application state and drawing commands. Tang Primer 20K and its 128 MB DDR3 hold assets and accelerate selected drawing operations. Existing MeOS GUI code is the starting point. Windows compatibility is not a goal.

DDR3 is an explicitly transferred external data region, not transparent CPU RAM. Initially use the existing Tab5 LCD through ESP32-P4. Image readback can limit performance; direct FPGA display needs separate hardware investigation. Spill/restore and compute buffers remain supporting research topics.

  1. Reproduce the Tab5 build; measure CPU rendering and RAM usage.
  2. Verify FPGA round trips, DDR3 integrity and effective bandwidth.
  3. Implement rectangle fills and image copies, then present results on Tab5.
  4. Integrate CPU/FPGA rendering backends, input, windows and menus; evaluate resident assets and dirty regions.
  5. Expand to compositing, scaling and compute acceleration based on measurements.

The first milestone is an interactive window and menu with at least one FPGA drawing operation. Speed improvement must be measured separately.

USB implementation reference

The official M5Stack Tab5 UserDemo uses ESP-IDF USB Host/HID drivers with FreeRTOS tasks. Tab5thinclient uses TinyUSB Host HID/MSC APIs. This fork uses its native Buffer DMA driver with split transactions for mixed-speed hubs. Following TinyUSB 0.19.0, the native HAL now waits for host mode before configuring FIFOs. USB writes, complete readback and persistence after reset passed on the corrected driver. ESP-IDF provides PHY initialization and DWC2 HAL services; the FreeRTOS scheduler is not used. The TinyUSB OS_NONE/FIFO implementation remains available for comparison. See the DMA investigation.

References: official Tab5 USB implementation, TinyUSB DWC2 host.

USB hubs and simultaneous devices

Implemented one external hub, port power, connection-change/reset handling, address allocation, per-device DATA PID tracking and independent MSC mounts. Two exFAT/FAT drives on a full-speed hub passed 512/8192 byte write/read, persistence after reset, volume isolation and simultaneous SD access. Hub keyboard command input passed on a separate DMA channel; sustained input under load and storage hot-plug remain pending. A USB microSD reader was mounted and listed without writing the card. The native lsusb command shows cached topology and mounts. See the hub record and diagnostics.

Execution order: USB receiver/storage, microSD, USB write correction and hub/multiple devices, concurrent SSH server/client, touch scrolling, Bluetooth keyboard/mouse.

USB 2.0 High-Speed hubs (480 Mbit/s) are an explicit requirement, including mixed high-speed drives and full/low-speed keyboards or receivers. Buffer DMA and Transaction Translator handling are implemented. The 0bda:5411 High-Speed hub enumerated two drives, a Full-Speed receiver and Ethernet; keyboard input and shell execution passed. Storage write/read regression on the new engine remains pending. See Espressif limitations.

Shared terminal and compatibility

Share terminal processing between the local console and SSH client. Implement VT100 as the baseline, then required VT220 features and selected xterm extensions. The SSH server must handle terminal type, PTY size, resize notifications and session I/O.

  • Verify cursor movement/save/restore, line/screen erase, text attributes/colors, scrolling regions, autowrap and DEC special graphics.
  • Implement arrows, editing/function/modifier keys and application cursor/keypad modes.
  • Add alternate screen, 256/RGB colors, bracketed paste and mouse reporting as needed. Full VT220 or xterm compatibility is not yet promised.
  • Integrate scrollback and touch input; test fragmented control sequences, UTF-8 and resizing. Match TERM and terminal replies to actual support; do not advertise xterm-256color prematurely.
  • Verify with vttest and remote Vim, nano, less and top. Remote applications are separate from native application ports.

Reference: XTerm Control Sequences. Develop the common terminal alongside concurrent SSH, before touch scrolling.

USB and built-in cameras

Native UVC supports uncompressed YUY2 using High-Speed isochronous Buffer DMA with one to three transactions per service interval. One 160×120 frame from 056e:700a was saved as BMP and read back. Continuous video, hot-plug and other devices are unverified; MJPEG, audio and bulk video are unsupported.

The native SC202CS CSI/ISP path passed capture, microSD BMP save, readback and restart. The USB UVC path passed one-frame capture and BMP readback but takes about 8–10 seconds per complete frame. Nonuniform stored pixels were verified; visual quality and sustained video operation remain unverified. The paths share BMP handling but retain separate capture transports. See the native camera record and USB camera record.

Keep the existing USB, microSD, hub, SSH, touch and Bluetooth priorities. Terminal compatibility belongs alongside SSH; camera work proceeds in parallel where dependencies allow. Set performance, format support and dates after measurement.

Storage over SSH and Linux mounting

MeOS now provides a standard SFTP v3 subsystem restricted to /sd, /usb and /usb1–/usb3. Storage export defaults to read-only; change policy with sshd storage ro|rw|off only while the server is stopped. FAT exclusive creation is atomic and takes precedence over truncation; unsupported EXCL on M5FS/devfs is rejected.

The standalone Python standard-library/OpenSSH helper uses connect HOST ROOT MOUNTPOINT to try existing SSHFS/FUSE and falls back to interactive file transfer. Separate ls/get/put/mkdir/rm commands are also available. Mounts default to read-only and require --rw for writes. Normal SSH host-key checks and authentication remain in force; no automatic installation or sudo is used. See the helper specification.

  • Actual-engine, FAT-adapter, fragmented-wire, exclusive-create and partial/failure cleanup host tests passed, as did the complete target build. A local-engine SD hardware self-test passed a fresh 8192-byte write/read at /sd/sftp_00ddb817.bin, existing-file EXCL refusal and unchanged contents on reread. This test excludes SSH transport/authentication. Hardware Wi-Fi SFTP passed two 102400-byte SD roundtrips with Paramiko and the actual helper client class, EXCL refusal/content preservation, delete/reconnect and read-only listing/write rejection. The serial SHA256 host-key fingerprint was compared before authentication. The actual helper process with Windows OpenSSH 9 passed an exact 20480-byte SD put/get and ls/rm using fingerprint-verified isolated known_hosts without changing user SSH settings. Actual Linux process/FUSE tests and USB network transfers remain unverified. SSH close now drains queued replies and exchanges exit-status/EOF/CLOSE before waiting for peer CLOSE; 14 encrypted host cases, including 33 pipelined replies, passed. Final firmware is 1,410,224 bytes.
  • Linux must initially reach the Tab5 SSH server. Reverse export through an SSH connection initiated by Tab5 is not implemented.
  • The SSH server currently accepts one inbound connection. A mount occupies it, preventing another remote Shell/transfer; the device local console remains usable. Independent channels and simultaneous access require further work.
  • Rename, arbitrary truncation and unsupported attributes fail explicitly. Even write-enabled mounts may not support editor temporary-file replacement. put requires --overwrite for an existing destination and only succeeds when the server supports the requested operation.
  • Validate media absence/removal, disconnect/reconnect, unmount, concurrent access and sustained transfers on hardware. Remote image transfer/display remains planned.

MicroPython and GPIO

The initial native MicroPython v1.26.1 port connects MeOS tasks, memory, console and VFS without the upstream ESP32 FreeRTOS port or WASM. It provides REPL, file execution and python -c, a 512 KiB PSRAM GC heap and a 32 KiB task stack. The complete target build and flashing passed. Hardware REPL checks passed 2**80, math.sqrt(9) and GC. The input-only smoke.py passed GPIO16, ADC16/53, reserved/duplicate/released-object rejection and 40 GC pressure cycles. The SD script /sd/mpqa_6adb51fa.py passed sibling-module import (value123), exclusive 1024-byte binary file write/read, seek/tell, a 24-byte tail read and context-managed close. Pin reclaim in the next VM after an intentional RuntimeError passed, as did restart after a 1 MiB bytearray MemoryError and Ctrl-C interruption of an infinite loop followed by shell return/new VM execution. These verify the initial feature scope; long-duration use and external output waveforms remain unverified. Initial firmware size was 1,396,080 bytes, 165,280 bytes above the previous SFTP build. The peripheral/time extension is 1,402,544 bytes, adding 6464 bytes. See the MicroPython implementation record.

Shared owner/pin-management and shell services now cover GPIO, uncalibrated ADC, PWM, SoftI2C, SoftSPI and UART1. Actual-code host tests and the whole target build passed. Python machine.Pin and uncalibrated ADC bindings are implemented; PWM/UART/SoftI2C/SoftSPI and monotonic time bindings are now implemented; IRQ remains pending. VM teardown closes the common IO owner and releases its pins. Input/ADC and GC pressure passed on hardware. Expansion functional tests passed the actual 32-bit VM with IO mocks (156 calls, eight accepted UART bytes); hardware passed no-output PWM/UART/bus safety checks and time range/wrap/delay, including Ctrl-C from a 60-second sleep in about 0.125 seconds. External PWM/UART/I2C/SPI wiring and waveforms remain unverified. Device reserved-pin refusal, GPIO16 input/release/reset, raw ADC16/53 acquisition and UART internal loopback passed; ADC35 was rejected. Floating ADC inputs do not establish voltage accuracy. External electrical timing and fixture tests remain unverified; hardware bus acceleration and interrupt-driven GPIO are future work. General-purpose DAC is excluded because the SoC has none. See the IO implementation plan, shared API and shell, and software protocol specification.

  • Map external connectors to GPIO numbers, supported modes, reserved roles and current owners.
  • Reject conflicts with LCD, PSRAM, Wi-Fi, storage, keyboards and FPGA.
  • Shell adapters provide io help, io pins, gpio, adc, pwm, i2c, spi and uart. Inspect ownership/reservations before changing a pin; use the help output for current syntax.
  • Pin bindings reject duplicate objects, reserved pins, other owners and released objects. Objects abandoned to GC retain resources until VM exit; explicit deinit is recommended. Validate normal exit, exceptions, Ctrl-C and a fresh VM. Forced task termination is not a supported shutdown method.
  • Verify valid/invalid pins, modes, pulls, ownership conflicts and repeated execution. Check wiring and voltage conditions before connecting hardware.

CPython and Pyxel: existing games without preprocessing

The goal is to run published Pyxel Python source and assets without per-game C/C++ or WASM conversion or asset preprocessing. Porting CPython and Pyxel itself is the primary candidate, separate from the MicroPython/GPIO work. Full compatibility and smooth performance remain unverified.

  • Pin CPython and Pyxel versions. Audit Python bindings, Rust standard-library/target support, SDL2/OpenGL and other dependencies. Investigate native execution on MeOS; existing browser WASM is not directly usable.
  • Connect CPython memory, files and time to MeOS; adapt Pyxel display, input, audio and file interfaces. Distinguish interpreted game logic from native engine work.
  • Start with the official Jump Game, then Platformer, using original Python and .pyxres files. Check held/pressed keys, transparency, flips, camera, tilemaps, mutable image banks, text, random numbers, music and effects.
  • Measure startup/runtime peak memory for CPython, Pyxel, assets, frames and audio against 32 MB PSRAM and internal RAM limits. FPGA DDR3 remains explicit-transfer storage, not an automatic extension of the Python heap.
  • Establish compatibility with CPU rendering before adding FPGA support. Preserve the original logical resolution and evaluate scaling, copies and compositing.

Validation and priorities

Measure command transfer, FPGA execution, image readback and LCD presentation together. Record FPS, input latency, CPU load, internal RAM/PSRAM use and traffic. Align inputs, precision and transfer conditions with the separate Linux repository; Linux drivers cannot simply be reused.

Prepare ESP-IDF v5.4.4 and reproduce sh tools/build.sh tab5 build; record artifact hashes. Before flashing, check existing firmware/C6 state and recovery. Check carrier pin conflicts, PARLIO, DMA, interrupts, cache synchronization and scheduler cooperation.

Advance input and microSD/FAT alongside GUI/FPGA work. Build common GPIO management before Python GPIO; expand storage mounting from SD reads to writes and USB. Stage mouse, terminals, BLE and app ports around dependencies. Set dates and performance targets after baseline measurements.

Proposal: external Japanese font storage

Store Japanese fonts on microSD and load them into FPGA DDR3 during startup. This is a proposal, not an implemented or finalized design; Tab5 microSD, FPGA transport and DDR3 support are prerequisites.

  • The current embedded font array is 467,155 bytes (about 456 KiB). Removing it mainly saves flash, not an equal amount of internal RAM.
  • For CPU rendering, fetch required glyphs and cache them on Tab5; evaluate the existing roughly 9 KiB cache, indexing, compression access and transfer latency.
  • For FPGA rendering, investigate direct glyph access in DDR3. A dedicated memory region does not require a RAM-disk filesystem; choose based on the common storage design.
  • Keep a small built-in Latin font for startup/errors and provide fallback diagnostics for missing SD, invalid fonts or FPGA initialization failure.
  • Preserve font attribution/licenses; check format, version, size and integrity. Measure startup time, cache hit rate, glyph latency and flash/RAM savings.
