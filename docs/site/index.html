Tab5 MeOS FPGA Development Plan

Plan to add Tang Primer 20K rendering operations and external DDR3 buffers to MeOS on M5Stack Tab5. This document describes implementation status, architecture and validation requirements.

Baseline build, flashing, boot and serial shell verified. USB extensions are in development. FPGA communication and GUI extensions remain unverified.

Updated: 2026-10-23

Development order and progress

USB and later work proceed in the order shown. Status reflects evidence; no overall percentage or dates are committed.

  1. Baseline firmwareHardware checked (limited)

    Size-optimized firmware flashed; boot, mem, ps and ls verified. Full regression pending.

  2. 1. USB receivers and storageIn development / unverified

    Native DMA verified: 37, 512 and 8192 byte write/read and persistence. Reconnection corrected; one idle unplug/replug cycle passed remount, full original-file readback and a new 512-byte write/read. TinyUSB retained for comparison. Receiver regression pending.

  3. 2. microSDHardware checked (limited)

    Verified on hardware: SPI access, /sd FAT mount, listing, 38-byte test file write/read and persistence after reset, simultaneous /usb mount. Speed optimization and hot-plug unverified.

  4. 3. USB hubs, multiple drives and keyboard coexistenceIn development / unverified

    Full-speed hub: exFAT/FAT write/read, persistence, isolation and SD access verified. Wireless keyboard command input and four-file readback passed (12 cumulative errors after a test including replug). USB card-reader mount/listing and lsusb with a hub plus three drives also verified. Storage hot-plug, sustained input under load and high-speed mixed-speed operation remain pending. On a USB3 hub operating at USB2 High-Speed, both drives passed new 8192-byte write/read CRC checks.

  5. 3a. USB EthernetIn development / unverified

    RTL8153 CDC-ECM passed hardware link, DHCP, ping and SSH. Releasing the USB lock during MSC DMA waits enabled reads/writes on both drives alongside 20/20 ping replies per test with zero USB errors or drops. Long-duration and hot-plug continuity tests remain pending.

  6. 3b. Wi-Fi validationIn development / unverified

    Updated C6 over SDIO to the official MCU application. Reset persistence, Wi-Fi initialization, scanning, WPA2 association and DHCP passed. With Ethernet unplugged and inactive, Wi-Fi DNS resolution and HTTP 200 retrieval passed on hardware. Long-duration traffic and reconnect tests remain pending.

  7. 4. Concurrent SSH server and clientIn development / unverified

    Shared-console SSH server implemented. Hardware authentication, commands, reconnect, stop and outbound SSH while keeping inbound SSH active passed. TCP slots are separate from Web/Tailscale. Independent PTYs, exec and SFTP are not implemented.

  8. 4a. Shared terminal: VT100 / VT220 / xtermIn development / unverified

    LCD/SSH implement 256/RGB colors, scroll margins, line edits, cursor save/restore and alternate screens. SSH adds DSR, DECCKM and Vim key passthrough. Actual-parser host tests passed; device Vim/SL end-to-end checks and full VT220/xterm compatibility remain pending.

  9. 5. Touch and console scrollingIn development / unverified

    256-line colored history and swipe handling implemented. Initial device swipe failed because the GT911-only input driver did not recognize the ST7121 panel. ST7123-compatible input added; device recheck pending.

  10. 6. Bluetooth keyboard and mouseNot started

    Audit C6 transport; implement BLE HID discovery, pairing, reconnect and input. Assess Classic separately.

  11. 7. USB cameras (UVC)Not started

    Add UVC enumeration, video transport and buffers to the native USB DMA driver. Audit bulk/isochronous transfers and MJPEG/uncompressed formats per device. Verify preview, capture and hot-plug at low resolution first.

  12. 8. Tab5 built-in cameraNot started

    Validate the existing SC202CS/MIPI-CSI/ISP driver and camera app on hardware. Check initialization, preview, capture and cleanup; fix gaps. Evaluate a common application API with USB cameras.

Architecture and milestones

MeOS manages input, windows, application state and drawing commands. Tang Primer 20K and its 128 MB DDR3 hold assets and accelerate selected drawing operations. Existing MeOS GUI code is the starting point. Windows compatibility is not a goal.

DDR3 is an explicitly transferred external data region, not transparent CPU RAM. Initially use the existing Tab5 LCD through ESP32-P4. Image readback can limit performance; direct FPGA display needs separate hardware investigation. Spill/restore and compute buffers remain supporting research topics.

  1. Reproduce the Tab5 build; measure CPU rendering and RAM usage.
  2. Verify FPGA round trips, DDR3 integrity and effective bandwidth.
  3. Implement rectangle fills and image copies, then present results on Tab5.
  4. Integrate CPU/FPGA rendering backends, input, windows and menus; evaluate resident assets and dirty regions.
  5. Expand to compositing, scaling and compute acceleration based on measurements.

The first milestone is an interactive window and menu with at least one FPGA drawing operation. Speed improvement must be measured separately.

USB implementation reference

The official M5Stack Tab5 UserDemo uses ESP-IDF USB Host/HID drivers with FreeRTOS tasks. Tab5thinclient uses TinyUSB Host HID/MSC APIs. This fork is consolidating on its native descriptor DMA driver. Following TinyUSB 0.19.0, the native HAL now waits for host mode before configuring FIFOs. USB writes, complete readback and persistence after reset passed on the corrected driver. ESP-IDF provides PHY initialization and DWC2 HAL services; the FreeRTOS scheduler is not used. The TinyUSB OS_NONE/FIFO implementation remains available for comparison. See the DMA investigation.

References: official Tab5 USB implementation, TinyUSB DWC2 host.

USB hubs and simultaneous devices

Implemented one external hub, port power, connection-change/reset handling, address allocation, per-device DATA PID tracking and independent MSC mounts. Two exFAT/FAT drives on a full-speed hub passed 512/8192 byte write/read, persistence after reset, volume isolation and simultaneous SD access. Hub keyboard command input passed on a separate DMA channel; sustained input under load and storage hot-plug remain pending. A USB microSD reader was mounted and listed without writing the card. The native lsusb command shows cached topology and mounts. See the hub record and diagnostics.

Execution order: USB receiver/storage, microSD, USB write correction and hub/multiple devices, concurrent SSH server/client, touch scrolling, Bluetooth keyboard/mouse.

USB 2.0 High-Speed hubs (480 Mbit/s) are an explicit requirement, including mixed high-speed drives and full/low-speed keyboards or receivers. Descriptor DMA cannot perform split transactions; add buffer DMA and Transaction Translator handling to the native driver. Full-speed hub results do not verify high-speed hubs. The current test hub, 05e3:0606, enumerates at full speed; high-speed and mixed-speed operation remain unverified. See Espressif limitations.

Shared terminal and compatibility

Share terminal processing between the local console and SSH client. Implement VT100 as the baseline, then required VT220 features and selected xterm extensions. The SSH server must handle terminal type, PTY size, resize notifications and session I/O.

  • Verify cursor movement/save/restore, line/screen erase, text attributes/colors, scrolling regions, autowrap and DEC special graphics.
  • Implement arrows, editing/function/modifier keys and application cursor/keypad modes.
  • Add alternate screen, 256/RGB colors, bracketed paste and mouse reporting as needed. Full VT220 or xterm compatibility is not yet promised.
  • Integrate scrollback and touch input; test fragmented control sequences, UTF-8 and resizing. Match TERM and terminal replies to actual support; do not advertise xterm-256color prematurely.
  • Verify with vttest and remote Vim, nano, less and top. Remote applications are separate from native application ports.

Reference: XTerm Control Sequences. Develop the common terminal alongside concurrent SSH, before touch scrolling.

USB and built-in cameras

Add UVC support to the native USB DMA driver. Inspect device descriptors and supported transport, formats, resolutions and frame rates. Implement bulk/isochronous video transfers as required; handle frame boundaries, loss, bandwidth, cache synchronization and removal. Evaluate MJPEG decoding and uncompressed conversion separately, starting with low-resolution, low-frame-rate preview and capture. Compatibility with all USB cameras is unverified.

The existing Tab5 SC202CS/MIPI-CSI/ISP driver and camera app need hardware validation in this fork. Check initialization, preview, capture, repeated start/stop and cleanup; fix gaps. Validate the separate USB and built-in paths before considering a shared frame API and GUI integration.

Keep the existing USB, microSD, hub, SSH, touch and Bluetooth priorities. Terminal compatibility belongs alongside SSH; the two camera milestones follow Bluetooth. Set performance, format support and dates after measurement.

Storage mounted from the SSH server

Use Tab5_thinclient as a reference. A FUSE helper on the connected Linux server mounts Tab5 microSD and USB storage as ~/sd and ~/usb. A separate SSH channel connects the helper to MeOS VFS. Linux and FUSE stay on the server. Audit Python/FUSE prerequisites, helper compatibility and reuse terms.

  • Start with read-only SD access, then writes, attributes, create/truncate/rename/delete, directories and USB storage.
  • Restrict exported roots and offer read-only/read-write access. Coordinate local/remote access and caches; define write completion and synchronization.
  • Handle media absence/removal, SSH disconnect/reconnect, helper exit and unmount. Never report unfinished writes as successful.
  • Verify file contents and interrupted transfers. Add SCP-style file transfer and remote image display.

MicroPython and GPIO

Integrate MicroPython with MeOS tasks, memory, console and VFS. Audit FreeRTOS dependencies before adapting ESP32 ports or Tab5_thinclient code. Provide REPL, scripts, Ctrl-C, exceptions and cleanup; measure GC heap and task stack use.

Share a MeOS pin-management API between Python and the shell. Begin with digital input/output and pulls; evaluate PWM, ADC, interrupts, I2C and SPI later.

  • Map external connectors to GPIO numbers, supported modes, reserved roles and current owners.
  • Reject conflicts with LCD, PSRAM, Wi-Fi, storage, keyboards and FPGA.
  • Proposed commands: gpio list, gpio mode, gpio read, gpio write, gpio release (not available yet).
  • Aim for basic machine.Pin compatibility. Define output state and ownership on exit, exception and interruption; define shell pin lifetime.
  • Verify valid/invalid pins, modes, pulls, ownership conflicts and repeated execution. Check wiring and voltage conditions before connecting hardware.

CPython and Pyxel: existing games without preprocessing

The goal is to run published Pyxel Python source and assets without per-game C/C++ or WASM conversion or asset preprocessing. Porting CPython and Pyxel itself is the primary candidate, separate from the MicroPython/GPIO work. Full compatibility and smooth performance remain unverified.

  • Pin CPython and Pyxel versions. Audit Python bindings, Rust standard-library/target support, SDL2/OpenGL and other dependencies. Investigate native execution on MeOS; existing browser WASM is not directly usable.
  • Connect CPython memory, files and time to MeOS; adapt Pyxel display, input, audio and file interfaces. Distinguish interpreted game logic from native engine work.
  • Start with the official Jump Game, then Platformer, using original Python and .pyxres files. Check held/pressed keys, transparency, flips, camera, tilemaps, mutable image banks, text, random numbers, music and effects.
  • Measure startup/runtime peak memory for CPython, Pyxel, assets, frames and audio against 32 MB PSRAM and internal RAM limits. FPGA DDR3 remains explicit-transfer storage, not an automatic extension of the Python heap.
  • Establish compatibility with CPU rendering before adding FPGA support. Preserve the original logical resolution and evaluate scaling, copies and compositing.
  • Compare frames and game state against the PC version using the same inputs; check audio/input and measure frame time, latency and memory. Target each game's original update rate and report compatibility and acceleration separately.
  • Record external Python/OS dependencies, Pyxel version differences, and game/asset usage and redistribution terms per title.

References: Pyxel, Jump Game, Platformer.

Validation and priorities

Measure command transfer, FPGA execution, image readback and LCD presentation together. Record FPS, input latency, CPU load, internal RAM/PSRAM use and traffic. Align inputs, precision and transfer conditions with the separate Linux repository; Linux drivers cannot simply be reused.

Prepare ESP-IDF v5.4.4 and reproduce sh tools/build.sh tab5 build; record artifact hashes. Before flashing, check existing firmware/C6 state and recovery. Check carrier pin conflicts, PARLIO, DMA, interrupts, cache synchronization and scheduler cooperation.

Advance input and microSD/FAT alongside GUI/FPGA work. Build common GPIO management before Python GPIO; expand storage mounting from SD reads to writes and USB. Stage mouse, terminals, BLE and app ports around dependencies. Set dates and performance targets after baseline measurements.

Proposal: external Japanese font storage

Store Japanese fonts on microSD and load them into FPGA DDR3 during startup. This is a proposal, not an implemented or finalized design; Tab5 microSD, FPGA transport and DDR3 support are prerequisites.

  • The current embedded font array is 467,155 bytes (about 456 KiB). Removing it mainly saves flash, not an equal amount of internal RAM.
  • For CPU rendering, fetch required glyphs and cache them on Tab5; evaluate the existing roughly 9 KiB cache, indexing, compression access and transfer latency.
  • For FPGA rendering, investigate direct glyph access in DDR3. A dedicated memory region does not require a RAM-disk filesystem; choose based on the common storage design.
  • Keep a small built-in Latin font for startup/errors and provide fallback diagnostics for missing SD, invalid fonts or FPGA initialization failure.
  • Preserve font attribution/licenses; check format, version, size and integrity. Measure startup time, cache hit rate, glyph latency and flash/RAM savings.
